# 10. Interrupts II

## Topics

- Pending status와 interrupt 응답
- Fault 및 supervisor call exception

## Pending Status

- Interrupt 요청이 들어오면 해당 interrupt가 pending 상태로 설정됨.
- NVIC의 Interrupt Set-Pending Register인 `ISPR`가 pending 상태 보관
- Interrupt source가 요청 신호를 해제해도 이미 설정된 pending 상태는 유지되며 handler 실행 가능
- Processor가 응답하기 전에 software가 pending 상태를 지우면 해당 요청 취소 가능
- Software가 pending bit를 직접 설정해 software interrupt 발생 가능

## Interrupt Inputs and Pending Behavior

| 상황 | Pending 및 active 상태 | 결과 |
| --- | --- | --- |
| 요청 신호 발생 | Pending 설정 | Handler 실행 대기 |
| 요청 신호 해제 | Pending 유지 | Handler 실행 가능 |
| 응답 전 pending 해제 | Pending 해제 | 요청 취소 |
| Handler 진입 | Active 설정, pending 자동 해제 | Handler 실행 |
| Handler 시작 전 여러 pulse | Pending 한 번 설정 | 한 번의 요청으로 처리 |
| Handler 도중 요청 신호 재발생 | Active 상태에서 pending 재설정 | 종료 후 handler 재진입 |
| 요청 신호가 계속 active | Handler 종료 시 다시 pending | Handler 재진입 |

- Pending은 아직 처리되지 않은 요청, active는 현재 처리 중인 exception의 상태
- Handler 실행 중 같은 interrupt가 다시 pending될 수 있으므로 두 상태가 동시에 존재 가능

## Nested Interrupts

- NVIC는 우선순위가 높은 interrupt가 낮은 우선순위의 handler를 선점하도록 지원
- Foreground 실행 중 `IRQ2` 발생 시 `ISR2` 실행
- `ISR2` 중 더 높은 우선순위의 `IRQ1` 발생 시 `ISR1` 실행 후 `ISR2` 재개
- 이후 `IRQ3` 처리 후 foreground 재개

## Interrupt Response: Tail Chaining

- 첫 handler가 종료될 때 다른 exception이 pending 상태라면 이전 context의 unstacking과 다음 context의 stacking 생략
- `SP`와 저장된 context를 유지하면서 `PC`와 `LR`을 다음 handler에 맞게 갱신
- 연속된 exception 사이의 응답 시간 단축

## Interrupt Response: Late Arriving

- 이전 exception의 stacking 도중 우선순위가 더 높은 interrupt가 도착하면 높은 우선순위의 handler를 먼저 실행
- 먼저 들어온 낮은 우선순위 exception은 이후 처리

## Interrupt Response: Pop Pre-emption

- Exception 종료를 위한 unstacking 중 새 exception이 도착하면 unstacking을 중단하고 새 handler 실행 시작

## Faults and Supervisor Call Exceptions

- Fault는 BusFault, MemManage Fault, UsageFault 및 HardFault로 구분
- OS 기능 호출과 지연된 작업 수행에는 `SVC`와 `PendSV` 사용

## Bus Faults

- AHB interface의 전송에서 오류 응답을 받으면 BusFault 발생
  - Instruction prefetch 오류
  - Data read 또는 write 오류
  - Exception stacking 오류
  - Exception unstacking 오류
- 원인 확인에 Bus Fault Status Register 사용
  - 유효하지 않은 memory 영역 접근
  - 아직 준비되지 않은 target device 접근
  - 지원하지 않는 전송 크기 또는 privilege level로 target device 접근

## Memory Management Faults

- 원인 확인에 Memory Management Fault Status Register 사용
  - MPU 설정에 정의되지 않은 memory 영역 접근
  - 실행 불가능한 memory 영역의 code 실행
  - Read-only 영역에 기록
  - Unprivileged 상태에서 privileged 전용 영역 접근

## Usage Faults

- 원인 확인에 Usage Fault Status Register 사용
  - 정의되지 않은 instruction 실행
  - Cortex-M3가 지원하지 않는 coprocessor instruction 실행
  - `PC`의 최하위 bit가 `0`인 주소로 이동하여 ARM state 전환 시도
  - 유효하지 않은 `LR` 값으로 exception return 시도
  - Multiple load/store에서 정렬되지 않은 memory 접근
  - 다른 interrupt가 active인 상태에서 Thread mode로 복귀 시도
- NVIC의 해당 제어 bit를 설정하면 다음 상황에서도 UsageFault 발생
  - `0`으로 나누기
  - 모든 종류의 정렬되지 않은 memory 접근

## Hard Faults

- UsageFault, BusFault 또는 MemManage Fault를 처리할 수 없으면 HardFault 발생
- 원인 확인에 Hard Fault Status Register 사용
  - Bus fault로 vector table entry를 읽지 못함.
  - 더 높은 우선순위의 fault handler에서 다른 fault가 발생함.

## SVC and PendSV

- `SVC`와 `PendSV`는 OS를 위한 exception
- `SVC` instruction 실행으로 SVCall 발생
- Interrupt Control and State Register인 `ICSR`의 `PENDSVSET` bit 설정으로 PendSV 발생

## SVC

- Unprivileged user program이 `SVC`를 통해 privileged kernel의 OS API 요청
- Kernel의 device driver가 hardware 및 peripheral과 통신
- User program이 hardware의 세부 제어 방식을 알 필요가 없어 software 이식성 향상

      ┌──────────────────┐  SVC   ┌──────────────────┐  API   ┌─────────────────┐
      │User program      ├───────▶│Privileged kernel ├───────▶│Device driver    │
      └──────────────────┘        └──────────────────┘        └────────┬────────┘
                                                                       │
                                                                       ▼
                                                              ┌─────────────────┐
                                                              │Hardware         │
                                                              └─────────────────┘

## PendSV

- PendSV는 낮은 우선순위로 설정하여 중요한 interrupt 처리 이후 실행 가능
- 대표적인 용도는 task 간 context switching
- `SysTick`이 직접 context switching을 수행하면 interrupt handler 실행 도중 task를 전환할 수 있음.
  - 아직 active인 interrupt가 있는데 Thread mode로 복귀하려 하면 UsageFault 발생
  - Task 전환 때문에 IRQ 처리가 지연될 수도 있음.
- 모든 interrupt handler가 끝날 때까지 전환을 단순히 기다리면 `SysTick`과 비슷한 빈도의 interrupt가 지속될 때 전환 지연 가능
- `SysTick` handler는 context를 직접 전환하지 않고 가장 낮은 우선순위의 `PendSV`만 pending으로 설정
- 높은 우선순위의 interrupt 처리가 모두 끝난 후 `PendSV` handler가 안전하게 context switching 수행

## Summary

- Pending, active 및 중첩 interrupt 상태
- Tail chaining, late arriving 및 pop pre-emption
- BusFault, MemManage Fault, UsageFault, HardFault
- `SVC`와 `PendSV`를 이용한 OS 서비스 및 context switching
